# footballProvider — FOOT AI NEWS

Module autonome fournissant des données football **réelles** à FOOT AI NEWS,
et le détecteur d'événements qui déclenche la génération de contenu IA.

## Quelle API est utilisée, et pourquoi

**API-Football** (opérée par API-Sports) : https://www.api-football.com

Couverture : plus de 1200 compétitions, matchs en direct (score, minute,
événements), compositions, statistiques, classements, calendrier et
résultats. C'est un service réel, payant au-delà du plan gratuit, choisi
parce qu'il couvre tout ce que demande le cahier des charges FOOT AI NEWS
**sauf une chose : les actualités éditoriales** (articles sur les clubs et
joueurs). Aucune API de données sportives ne fournit ce type de contenu —
il faudra brancher une source séparée (flux RSS de médias sous licence, ou
une API de presse comme NewsAPI) pour la section "Actualités" du cahier des
charges. Ce module ne s'occupe que des données de match/compétition.

### Obtenir une clé API

1. Créer un compte sur https://dashboard.api-football.com/register (gratuit,
   sans carte bancaire).
2. La clé API apparaît directement dans le tableau de bord.
3. La copier dans `FOOTBALL_DATA_API_KEY` (voir `.env.example`) — **jamais**
   dans le code, jamais commitée dans le repo.

### Plans et limites (à vérifier sur le site avant mise en production, les
tarifs évoluent)

| Plan | Requêtes/jour | Limite/minute |
|---|---|---|
| Free | 100 | 10 |
| Pro | 7 500 | 300 |
| Ultra | 75 000 | 450 |

Le plan gratuit suffit pour développer et tester, pas pour suivre plusieurs
matchs en direct en production — le système de cache de ce module est conçu
pour limiter la consommation de quota (voir plus bas), mais un plan payant
sera nécessaire pour un usage réel.

### Authentification

Deux façons de s'abonner à API-Football : directement sur api-football.com,
ou via RapidAPI. Ce module utilise la voie directe :

```
Header : x-apisports-key: VOTRE_CLE
```

## Installation

```bash
cd football-provider
npm install
cp .env.example .env
# éditer .env et renseigner FOOTBALL_DATA_API_KEY
```

## Utilisation

```ts
import { createFootballProvider } from './src/ProviderFactory';

const provider = createFootballProvider(); // lit FOOTBALL_PROVIDER / FOOTBALL_DATA_API_KEY / DEMO_MODE

const liveMatches = await provider.getLiveMatches();
const events = await provider.getMatchEvents(liveMatches[0].id);
```

Pour changer de fournisseur plus tard (ex. Sportmonks), il suffit d'ajouter
une nouvelle classe dans `src/providers/` implémentant l'interface
`FootballProvider` (définie dans `src/types.ts`), puis un nouveau `case`
dans `ProviderFactory.ts`. Aucun autre fichier de l'application n'a besoin
d'être modifié.

## Mode démonstration

```
DEMO_MODE=true
```

Force l'utilisation de `MockFootballProvider`, avec des données clairement
fictives (préfixées `demo-`). Ce mode ne doit **jamais** être actif en
production, et la couche de publication Facebook doit elle-même vérifier ce
flag avant tout envoi réel (voir le document d'architecture principal,
section 11).

## Le détecteur d'événements (EventDetector)

`src/eventDetector/EventDetector.ts` interroge périodiquement les matchs en
direct, compare les événements reçus à ceux déjà enregistrés (via
`EventRepository`, à implémenter avec Prisma dans l'application réelle), et
transmet chaque nouvel événement à un `EventPublisher` (à implémenter avec
une file BullMQ) qui déclenche la génération de publication IA.

Exemple d'implémentation Prisma pour brancher le détecteur à la vraie base :

```ts
const repository: EventRepository = {
  exists: (id) => db.matchEvent.findUnique({ where: { id } }).then(Boolean),
  save: (event, priority) => db.matchEvent.create({ data: { ...event, priority } }),
};

const publisher: EventPublisher = {
  publish: (event, priority) => queue.add('generate-post', { eventId: event.id, priority }),
};

const detector = new EventDetector({ provider, repository, publisher });

// Appelé toutes les 20-30s par un job planifié (cron ou BullMQ repeatable job)
setInterval(() => detector.pollLiveMatches(), 25_000);
```

### Priorités des événements

- **urgent** : but, but contre son camp, penalty marqué, carton rouge, fin de match
- **important** : carton jaune, remplacement, VAR, penalty manqué
- **normal** : coup d'envoi, mi-temps, reprise, temps additionnel, coup franc

## Cache

Chaque méthode de `ApiFootballProvider` passe par un cache avant tout appel
réseau (voir `src/cache.ts`). `MemoryCache` (en mémoire, par processus) est
fournie par défaut et suffit en développement. En production avec plusieurs
instances du backend, remplacer par une implémentation Redis respectant la
même interface `Cache` (`get`, `set`, `del`).

Durées de cache par défaut :

| Donnée | TTL |
|---|---|
| Matchs en direct | 30 s |
| Événements de match | 20 s |
| Compositions | 5 min |
| Statistiques | 30 s |
| Calendrier / résultats | 1 h |
| Classements | 30 min |
| Compétitions | 24 h |

## Gestion des erreurs

- `ProviderAuthError` : clé API absente ou invalide — ne jamais retenter.
- `RateLimitError` : quota ou limite par minute atteinte — ne jamais retenter
  automatiquement ; à surveiller via `Log` côté application.
- `ProviderUnavailableError` : panne réseau ou erreur serveur — 2 tentatives
  avec backoff exponentiel avant abandon.
- `NotFoundError` : ressource inexistante chez le fournisseur.

## Ce que ce module ne fait jamais

- Il n'invente aucune donnée. Un champ absent de la réponse API devient
  `null`, jamais une valeur estimée.
- Il ne classe un événement dans un type précis (but, carton, penalty...)
  que si le libellé brut du fournisseur correspond explicitement ; un
  libellé non reconnu n'est pas deviné.
- Les coups francs (`free_kick`) ne sont produits que si le fournisseur
  envoie littéralement ce libellé — API-Football ne le fait pas nativement,
  ce type restera donc rarement peuplé avec ce fournisseur.
- `MockFootballProvider` ne peut pas être sélectionné silencieusement en
  production : il faut soit `DEMO_MODE=true`, soit `FOOTBALL_PROVIDER=mock`
  explicitement.

## Tests

```bash
npm test
```

Les tests (`tests/*.test.ts`, Vitest) mockent entièrement `fetch` — aucun
appel réseau réel n'est effectué, aucune clé API n'est nécessaire pour les
faire tourner. Ils couvrent :

- la conversion correcte des réponses API-Football vers les types du domaine ;
- le respect du principe "champ manquant → null, jamais deviné" ;
- le cache (pas de second appel réseau pour une donnée déjà en cache) ;
- la gestion des erreurs 401/429/5xx et les retries ;
- la distinction but normal / penalty / but contre son camp ;
- l'idempotence du détecteur d'événements (un événement n'est jamais publié deux fois) ;
- l'attribution correcte des priorités urgent/important/normal ;
- la résilience du détecteur quand un match échoue sans bloquer les autres.
